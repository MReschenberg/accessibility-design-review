Accessibility Design Review: Containers — secondary (non-color) identifiers

Figma: Containers
Page reviewed: A11y Review — June 09, 2026 (three idea sheets: Pattern, Tab Hover Preview, “Counting” Dots)
Platform: Desktop (Firefox chrome — horizontal & vertical tabs)
Reviewer: Claude Code (Mozilla accessibility team)

What’s covered

This sheet explores three ways to let people tell Containers apart by something other than the container’s colored line — the core of WCAG 1.4.1 Use of Color, since a color-only indicator excludes color-blind and many low-vision users. Idea 01 (Pattern) adds a line-style chooser (“Solid line”, dashed, dotted…) to the top-border indicator; Idea 02 (Tab Hover Preview) adds the container icon (and optionally title) to the tab hover card; Idea 03 (“Counting” Dots) adds a row of small dots to the top border. Each is shown on the LinkedIn mock in both horizontal- and vertical-tab layouts, plus an “Add New Container” dialog. This is a follow-up review: there is an active thread of unresolved accessibility comments from Morgan Rae Reschenberg, all folded into the findings below so you have one complete list. The overall direction — adding a second, non-color channel — is exactly right; the findings are about making each channel actually perceivable and exposed to assistive tech.

Findings

1. Container identity must reach screen-reader users regardless of the visual treatment — S2

All three ideas are visual secondary indicators; none of them, on their own, tells a screen-reader user which container a tab belongs to. The container name needs to be part of the tab’s accessible name in both horizontal and vertical tabs. Today it is exposed on horizontal tabs in Nightly but not on vertical tabs; parity is required before this migrates into core. See the vertical-tab mock. (Previously raised by @Morgan Rae Reschenberg)

2. The colored top-border indicator does not meet non-text contrast — S2

The thin colored line that marks a container is a meaningful UI indicator, so it must meet WCAG 1.4.11 Non-text Contrast (3:1) against its adjacent background — and it does not for several of the default swatches, in light mode especially. One measured combination sits at ~1.9:1 in light mode, and another at ~2.75:1. Because these are the colors we ship as choices, every default swatch needs to pass 3:1 in both light and dark default themes. See the indicator on the Pattern sheet. (Previously raised by @Morgan Rae Reschenberg; light-mode value here and near-miss here.)

3. Container icons on their colored backgrounds don’t meet 3:1 — S2

The container icon rendered on its colored chip is a non-text element and must clear 3:1. At least one icon/background pair fails today, and we don’t yet have mocks of the full icon set on each colored background in both pressed and non-pressed states to confirm the rest. Please provide those combinations so every default pairing can be verified. See the Add New Container dialog and the tab chips. (Previously raised by @Morgan Rae Reschenberg.)

4. “Add New Container” dialog must manage focus as a blocking modal — S2

The dialog needs full keyboard/screen-reader focus management: trap focus while open, close on Esc, and return focus to the control it launched from. Since it opens from a context menu, landing focus back on the tab is the right target. It should also be blocking (a true modal). See the dialog. (Previously raised by @Morgan Rae Reschenberg.)

5. Color and Icon choosers should be true radio groups — S2

In the dialog, the Color row and the Icon row are each a single-select from a set — that is a radio group (role="radiogroup" with radio children), not a row of buttons. Only the selected swatch/icon should be a tab stop, and arrow keys should move selection. Right now the selected state is also shown only by a colored ring; add a non-color cue (e.g. a check) so selection isn’t conveyed by color alone (1.4.1). See the Color/Icon pickers. (Previously raised by @Morgan Rae Reschenberg.)

6. Every color and icon choice needs an accessible name — S3

The swatches and icons are presented visually only. Each color needs an exposed name (“Blue”, “Pink”…) and each icon needs a name (“Briefcase”, “Music”…) so screen-reader users can choose. In the resulting context-menu item, the recommended pattern is to keep the name as the plain text label and put the color + icon in the description. See the pickers. (Previously raised by @Morgan Rae Reschenberg: color names, icon names, menu-item exposure.)

7. Tab Hover Preview is hover-only — must also work on keyboard focus — S3

Idea 02 puts the container identity in the tab hover card. Hover isn’t available to keyboard or touch users, so the same preview must appear on keyboard focus, and per WCAG 1.4.13 it must be dismissable, hoverable, and persistent. The designer’s own note (“reduced scannability / required extra click”) reinforces that hover shouldn’t be the only path to container identity — it should supplement the always-visible indicator and the accessible name (Finding 1), not replace them. Of the two layouts shown, the version that groups the icon with the tab title is preferred for screen-magnifier users, since the icon and title stay together in the viewport. See the Tab Hover Preview sheet. (Previously raised by @Morgan Rae Reschenberg — recommend adopting the grouped version in 155.)

8. Container icons in High Contrast Mode should follow the system text color — S3

In HCM the container icons should render in the system text color (so they stay visible against the forced background), while the color swatches in the chooser keep their real colors as in non-HCM mode. No HCM variant of any of the three sheets is shown yet — please add one, since the thin colored indicators and icon chips are exactly the elements most likely to disappear when system colors are forced. See the indicator sheet. (Previously raised by @Morgan Rae Reschenberg.)

9. The container tab needs aria-haspopup="menu" and related attributes — S3

The tab control that opens the container context menu should advertise that it opens a menu (aria-haspopup="menu") along with the appropriate expanded/controls attributes, so screen-reader users know the affordance exists. See the tab strip. (Previously raised by @Morgan Rae Reschenberg.)

10. “Counting Dots” is the weakest of the three for low vision — S3

A row of small dots (each only a few pixels on the top border — see the dot indicator) asks the user to count to identify a container. People can reliably recognize a count at a glance only up to about four; beyond that it becomes a deliberate counting task, which is slow for everyone and unreliable at low visual acuity — and the designer’s own “might run out of dots” note reflects the same ceiling. It also carries no inherent text/programmatic value. If pursued, cap the count low, make each dot large enough to meet non-text contrast, and expose the number as text. The Pattern approach is stronger here because a line style (dashed/dotted) is a shape difference that also survives HCM — but a pattern on a ~2px line is hard to perceive, so pair it with a taller indicator and the icon rather than relying on the line alone. (Relates to @Morgan Rae Reschenberg’s concern that repeated small shapes won’t be differentiable on large screens.)

11. Split view must advertise each view’s container to screen readers — S3

When split view is active, a screen reader focusing the outer document should be told which container each “view” belongs to — otherwise the container distinction is lost the moment two are on screen together. See the review page. (Raised as a question by @Morgan Rae Reschenberg — see Questions.)

12. Deemphasized text uses alpha transparency — will lose contrast in HCM — S3

Several secondary strings are set with transparency rather than an opaque token — e.g. “Trending searches” and the hover-card “Description”/“Hint” and URL text at rgba(24, 14, 48, 0.7). On the current white surfaces this passes, but in High Contrast Mode the alpha is preserved and the text blends toward the forced background, so its contrast is no longer guaranteed. Use an opaque de-emphasized text token instead of an alpha value. See the tab-preview card. (New finding.)

13. “Pattern” vs “Secondary Indicator” — use one label — S4

The same dropdown is labeled Pattern on Idea 01 and Secondary Indicator on Idea 03. Pick one consistent label (“Secondary indicator” reads more clearly and doesn’t presume a line style) so the field name is stable for everyone, including screen-reader users hearing it announced. Compare Idea 01 dialog and Idea 03 dialog. (New finding.)

14. Color swatch / icon targets are at the minimum size — S4

The color swatches and icon buttons render at roughly 24 px. That meets the WCAG 2.5.8 (AA) 24 px minimum but leaves no margin, and they sit close together; nudging them toward 44 px (2.5.5, AAA) with a little more spacing would make the picker easier to operate for motor-impaired users. See the picker rows. (New finding.)

Questions for the designer

  1. Is the split-view container advertisement (Finding 11) something the add-on does today, or new work for the core migration? See the thread.
  2. Which of the three ideas is the intended direction — or are they meant to combine (e.g. icon + pattern + accessible name)? Our recommendation is to treat the accessible name as mandatory and layer icon + line pattern as the visible secondary channel, and to drop counting-dots.
  3. Do you have HCM and dark-mode variants of these three sheets we can review (Finding 8)?

14 findings (5 × S2, 7 × S3, 2 × S4), consolidating 12 still-open threads from Morgan Rae Reschenberg plus 3 new issues.
The strategic direction is right — adding a non-color channel is the correct fix for 1.4.1 — but the design isn’t ship-ready until the S2 items are resolved: the container name must reach screen-reader users on both tab orientations, the default indicator colors and icon chips must clear 3:1, the create/edit dialog must behave as a proper focus-managing modal, and the color/icon pickers must be real radio groups. Our recommendation is to make the accessible name mandatory and combine the icon with a line pattern as the visible secondary indicator, rather than relying on counting dots.
